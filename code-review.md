# Forex & Memecoin Trading Bot — Code Review

**Repository:** `gorefilip20/Forex-and-memecoin-trading-`
**Reviewed branch/commit:** `claude/elegant-dijkstra-q6h0ql` / `7b2883e`
**Review scope:** static review of Python, MT5 EA, configuration, execution, state, and risk paths. No broker, wallet, or live-trading credentials were accessed.

## Executive assessment

The code is a useful prototype with a coherent split between forex, Solana memecoin execution, Redis state, notifications, and an MT5 bridge. It passes Python bytecode compilation (`python3 -m compileall -q .`).

It is **not ready to be trusted with funded live trading**. The most serious issues are not cosmetic: the current implementation can mis-account risk, fail to track MT5 trades correctly, allow duplicate or inconsistent execution, and report misleading performance. These issues must be fixed and tested in paper/demo mode before any live deployment.

No code change was made during this review.

## Critical blockers

### 1. Daily drawdown protection is effectively disabled

`core/state.py` logs entries without a timestamp (`log_forex_trade` and `log_memecoin_trade`, lines 85–88 and 41–44). Exit events generated by the executors also do not add `timestamp` or `closed_at`.

`core/risk.py:60–63` only counts closed trades whose timestamp contains today's UTC date. Because the events have no timestamp, `check_daily_drawdown()` normally sees zero daily P&L and cannot reliably trip the configured drawdown limit.

**Fix:** make the logging layer append a server-generated UTC timestamp to every event; use an authoritative daily equity baseline plus realized and unrealized P&L; add tests crossing UTC midnight and tests for malformed events.

### 2. MT5 confirmation can create the wrong trade and lose state

`main.py:1142–1160` handles an MT5 EA fill by calling `ForexExecutor.open_position(..., paper_trading=False)`. That function sends an **OANDA order**, not an MT5 state reconciliation. Therefore:

- An MT5 trade can be followed by a second OANDA trade if OANDA credentials exist.
- If OANDA credentials are absent, `open_position()` returns `None`, but the endpoint still deletes the pending signal and returns `{"status":"confirmed"}`.
- The Redis position is not reliably created for the actual MT5 position.

**Fix:** separate `record_mt5_fill()` from broker order placement. The MT5 confirmation endpoint must only atomically consume a pending signal and record the actual MT5 ticket, symbol, side, volume, fill, SL, TP, and server time. It must never call the OANDA executor.

### 3. MT5 webhook is not replay-safe or race-safe

`get_signals` returns pending signals, and `confirm_trade` performs a separate read followed by delete (`main.py:1149–1156`). Two EA instances or a retry can confirm the same signal concurrently.

**Fix:** consume the pending signal with an atomic Redis transaction/Lua script, include a unique execution ID/idempotency key, and return the existing result on duplicate confirmation. Add a TTL and status transition (`pending → claimed → filled/failed`) rather than delete-on-request.

### 4. Position sizing is not actually risk-based

`ForexBotRequest` exposes `risk_per_trade_pct`, but `run_forex_cycle()` never uses it to calculate lot size. `ForexExecutor` scales the fixed lot size using AI confidence (`forex/executor.py:62–68`) instead.

The current risk formula assumes a simple `$10 per pip per lot` (`forex/executor.py:68`). That is not valid across:

- USD/JPY and other non-USD quote pairs
- EUR/GBP and other cross pairs
- XAU/USD and XAG/USD
- BTC/USD and ETH/USD CFDs
- broker-specific contract sizes and tick values

**Fix:** obtain symbol metadata and tick value from the actual execution venue, then calculate volume from account equity, risk percentage, stop distance, contract size, currency conversion, min/max volume, and volume step. AI confidence may filter trades, but must not silently increase financial risk.

### 5. Broker-side and local stops are not reconciled

The OANDA path places SL/TP at entry, but the local trailing/Jev logic later changes `pos["stop_loss"]` without modifying the broker-side order (`forex/executor.py:183–207`). The local state can show a tightened stop while the live broker position still has the original stop.

The local exit loop polls prices, so fast markets can move through a stop before the next cycle. The README acknowledges this limitation.

**Fix:** modify the broker-side protective order whenever a trailing stop changes; treat broker SL/TP as the primary protection; reconcile open positions and orders from the broker on every startup and cycle; fail closed if reconciliation is unavailable.

### 6. MT5 status endpoint contains a field-name bug

MT5 positions are written with `stop_loss` and `take_profit`, but `main.py:1172–1173` reads `p["sl"]` and `p["tp"]`. A status request containing a position can raise `KeyError` instead of returning status.

**Fix:** use one canonical schema and add an API integration test for `get_status` with an open position.

## High-priority issues

### 7. MT5 EA JSON parsing and symbol mapping are fragile

`mt5/TradingBotEA.mq5:63–83` uses substring parsing rather than a JSON parser. This can break with escaped values, unexpected field order, or formatting changes. It also maps `EUR/USD` to `EURUSD` without handling broker suffixes such as `.m`, `-ecn`, or `#`.

There is no validation that the signal's entry, stop, and target are on the correct side of the market, no volume normalization to broker min/step/max, and no check for an existing position with the same magic number and signal ID.

**Fix:** use a real MQL5 JSON parser or a minimal strict schema parser, add a configurable symbol map, normalize volume with `SYMBOL_VOLUME_*`, validate price/SL/TP against bid/ask and stop levels, and deduplicate by signal ID.

### 8. Live mode is still too easy to activate

The environment requires `FOREX_LIVE=true` plus `LIVE_TRADING_UNLOCK=true`, which is better than an accidental default. However, the MT5 bridge's `confirm_trade` only checks `LIVE_TRADING_UNLOCK`; it does not require `FOREX_LIVE=true`, `AUTO_TRADE=true`, or a per-account allowlist.

**Fix:** require an explicit market-specific live gate, broker-account identity check, deployment environment check, and a startup safety report. Default to demo/paper and reject production credentials in non-production environments.

### 9. No atomic concurrency control around cycles

Background loops, HTTP triggers, approval handlers, and the MT5 EA can overlap. Position-count checks and pending-signal checks are read-then-write operations. Two cycles can open more trades than `max_positions` or duplicate a signal.

**Fix:** add a distributed lock per market/cycle, atomic position reservation, idempotency keys, and a broker reconciliation worker. Test concurrent requests explicitly.

### 10. Performance analytics are misleading

`core/risk.py:207–211` calculates a Sharpe-like number from individual trade P&L values and annualizes with `sqrt(252)`, without a time interval or return denominator. This is not a valid Sharpe ratio.

`calculate_stats()` in `core/state.py` omits newer exit types such as `JEV_EXIT`, `TRAIL_STOP`, and `LADDER_EXIT`, while `calculate_analytics()` includes some of them. The dashboard and daily report can therefore disagree.

Memecoin live P&L uses estimated price-based proceeds (`memecoin/executor.py:237–238`) rather than confirmed on-chain token amounts, SOL/USD conversion, fees, priority fees, and actual swap output.

**Fix:** create one canonical trade-event schema and one analytics pipeline based on confirmed fills. Report realized P&L, fees, slippage, exposure, drawdown, expectancy, and time-based returns separately. Do not present a small live sample as proof of strategy profitability.

## Memecoin-specific concerns

- The configured default slippage is `700` bps (7%) and the model permits up to `2000` bps (20%). That is extremely permissive for live swaps.
- Jupiter price-impact filtering is present, but there is no clearly enforced maximum absolute loss in USD per trade or wallet-level daily loss circuit breaker.
- `_get_token_balance()` is used after a buy and before sells, but the position record does not consistently preserve decimals, actual received amount, fees, or the exact execution quote.
- A failed/unknown on-chain confirmation can leave Redis state inconsistent with the wallet. Reconciliation from chain balances and transaction metadata is required.
- The seed-phrase derivation is custom and should be replaced with a well-tested wallet derivation library/path matching the user's wallet. Never put a funded wallet's private key in application environment variables unless the user accepts the custody risk; a dedicated limited wallet is safer.

## Strategy and profitability findings

The presence of AI decisions, technical indicators, trailing stops, and a recent profitable period does **not** demonstrate a durable edge. The repository currently has no visible reproducible backtest harness, walk-forward report, out-of-sample result, Monte Carlo analysis, or cost/slippage sensitivity report.

Before claiming that the bot is profitable, produce:

1. A deterministic historical data snapshot and versioned strategy configuration.
2. In-sample, validation, and untouched out-of-sample periods.
3. Spread, commission, financing/swap, slippage, latency, and rejected-order assumptions.
4. Per-market and per-symbol results.
5. Maximum drawdown, recovery factor, profit factor, expectancy, exposure, turnover, and consecutive-loss distribution.
6. Walk-forward and parameter-perturbation results.
7. Paper/demo forward results with the same code path that would be used live.

It is not possible to guarantee “a lot of profitable records.” A robust system should instead prove that losses are bounded and that performance survives realistic costs and regime changes.

## Recommended implementation order

### Phase 1 — Safety and correctness

- Add canonical event schema with timestamps, IDs, source, order ID, fill, fees, and status.
- Fix daily drawdown calculation and use an equity baseline.
- Split MT5 fill reconciliation from OANDA order execution.
- Add atomic pending-signal consumption and cycle locks.
- Fix MT5 status field names and add tests.
- Disable all live flags by default in deployment.

### Phase 2 — Execution integrity

- Implement broker/MT5 startup and periodic reconciliation.
- Make protective stops broker-side and update them atomically.
- Implement venue-aware tick-value and volume sizing.
- Add idempotency and retry rules that cannot duplicate orders.
- Add alerts for stale data, disconnected broker, rejected orders, and state mismatch.

### Phase 3 — Visual dashboard

Build a read-only dashboard showing:

- Current mode: paper/demo/live lock state
- Broker/MT5 connectivity and last reconciliation time
- Pending signals, open positions, broker ticket IDs
- Entry, current price, SL, TP, distance to risk levels
- Realized/unrealized P&L, fees, slippage, drawdown
- Exposure by market, symbol, and direction
- Trade log and error/reconciliation history
- Kill switch and pause status

The dashboard should not be the authority for execution; the broker/MT5 account and reconciliation ledger should be authoritative.

### Phase 4 — Validation

- Unit tests for calculations and signal validation.
- Integration tests with mocked OANDA/Jupiter/MT5 responses.
- Concurrency and retry tests.
- Historical backtest and walk-forward evaluation.
- MT5 demo forward test.
- Only after passing those gates should the user independently decide whether to enable any live execution.

## Bottom line

The project can be improved into a safer dual-market research and paper-trading system, and a visual dashboard can be added. The current code should **not** be treated as a guaranteed-profit or production-safe live trader. The first implementation work should target the six critical blockers above, followed by tests and demo reconciliation—not strategy tuning or larger trade sizes.
